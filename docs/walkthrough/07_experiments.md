## 1. 通俗版

### 1.1 验收不是"跑通了"，而是"每条主张都有对应证据"

这个项目最特别的地方不是算法，而是它对"能说什么"的克制。仓库里几乎每份文档都有一节叫"不能声称"。

原因很实际：一个仿真结果可以被四种方式夸大——

| 夸大方式 | 例子 |
|---|---|
| 把 Python 当真实 | "54/54 通过"（其实是纯 Python，无 xdyn/Gazebo） |
| 把单次当分布 | "重复性良好"（其实只跑了一次） |
| 把控制当实测量 | "F0/F1/F2 都用实测流"（其实只有 F2，且 F2 的流没起来） |
| 把仿真当海试 | "系统已验证"（其实没有硬件） |

所以整个证据体系是**按"主张"分层**的，不是按"跑了多少次"分层。

### 1.2 三层证据，各自能证明什么

| 层 | 内容 | 能证明 | 不能证明 |
|---|---|---|---|
| **L1 Python** | `twin_axial_g12_matrix/python_20261110_01`：54 条（3 流 × 3 场景 × 6 初始） | 控制律 + 几何 + 自研物理的闭环可行性 | 6-DOF 耦合、推进器饱和、通信时延 |
| **L2 真实链路** | `g12_real_matrix_20261113_01`：54 条实际运行（xdyn + Gazebo + ROS） | 传输、分配、状态回写、原生进程行为 | 统计意义上的鲁棒性 |
| **L3 联合矩阵** | `s4_joint18_20261120_01`：18 + 27 repeat = 45 条（S4 D 路径 + v10 实测流） | 多障碍场景下的可重复性 | 18 真实矩阵、海试 |

关键分层数字：

| 集合 | 结果 | 口径 |
|---|---|---|
| G12 Python 矩阵 | **54/54** | 逐条全通过 |
| G12 真实矩阵 | **53/54** | 逐条；唯一失败 S1/F1/P4 |
| 真实矩阵的组口径 | 45 名义条目 **44/45**；九组 N6/R2 通过 | N6 = 每组 ≥ 4/5 且 P0 成功且无安全违规 |
| S3 名义场景真实 | **18/18** | S3 double_baffle_tight_v1 |
| S4 联合矩阵 | **18/18** | F0/F1/F2 × (P0–P4 + P0_repeat) |
| S4 联合 repeat | **27/27** | 每个初始 3 次，共 45 条 |

**注意"54/54"和"53/54"不能混用**，也不能把 N6 组口径写成"真实 54/54"——文档专门写了这句话。

### 1.3 七个指标，各有各的用途

| 指标 | 定义 | 用途 |
|---|---|---|
| `arrival_time` | 进入容差且保持 `settle_time` 的时刻 | 效率 |
| `min_clearance` | 执行轨迹全程最小障碍净距 | 安全 |
| `safety_margin` | `min_clearance − 0.9` | 安全余量 |
| `rms_error` | 相对参考的位置误差均方根 | 跟踪质量 |
| `max_error` | 最大位置误差 | 最坏情况 |
| `max_pitch` | 最大俯仰角 | 姿态包络 |
| `saturation_fraction` | `α < 0.999` 的步数占比 | 控制权限 |

阈值（`THRESHOLDS`）：

```
净空 ≥ 0.9 m     RMS ≤ 0.35 m     最大误差 ≤ 0.8 m
饱和 ≤ 20%       超时 300 s        俯仰 ≤ 75°      角速度 ≤ 0.8 rad/s
```

**为什么净空是 0.9 而规划用 1.5？** 因为两者语义不同：

- 规划净距 1.5 m = 车半径 0.7 + 安全裕量 0.8，是**设计余量**；
- 验收阈值 0.9 m = 车半径 0.7 + 0.2，是**不可再低的下限**。

中间 0.6 m 就是"允许跟踪误差吃掉的余量"。这也解释了为什么 S4 的实际净距 1.44–1.57 m 算"合格但不宽裕"。

### 1.4 一个必须自己算一遍的数据观察：F0 ≈ F2

18 矩阵里，F0（无流）与 F2（实测流）的结果几乎一模一样：

| 案例 | 到达 s | 净距 m | RMS m |
|---|---:|---:|---:|
| F0/P0 | 60.90 | 1.547738 | 0.145710 |
| F2/P0 | 60.90 | 1.547572 | 0.145741 |
| **差** | **0** | **0.00017** | **0.00003** |

而 F1（常流 0.05 m/s）差异明显：

| 案例 | 到达 s | 净距 m | RMS m |
|---|---:|---:|---:|
| F1/P0 | 60.65 | 1.472905 | 0.140111 |
| **F1 相对 F0** | −0.25 | **−0.075** | −0.006 |

**为什么 F2 和 F0 一样？** 算一下 v10 的流就知道：

```python
_gate(t) = 0.5·(1 + u/√(u²+0.01)),  u = (t − 105)/45
```

| t (s) | 0 | 30 | 60 | 61 | 90 | 105 | 120 | 150 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 流速 (m/s) | 1.5e-5 | −6e-5 | −3.3e-4 | **−3.5e-4** | −4.0e-3 | −0.115 | −0.266 | −0.314 |

任务在 **61 s** 结束，而流的 onset 在 **60–150 s**。所以整个任务窗口内，实测流的最大幅值只有 **0.35 mm/s**，是 F1 常流（50 mm/s）的 **0.7%**。

**结论（必须写进论文）**：F2 在 18 矩阵中确实是"实测流配置"，但**实测流在任务窗口内几乎未生效**。因此 18/18 不能用来支持"控制器对实测流鲁棒"这一主张。要看流的作用，只能看 F1。

这不是代码 bug，而是**实验设计的时间尺度错配**——数据本身能验证，所以能说清楚。

### 1.5 重复性：两个数不能混

| 数据 | 最大位置差 | 出处 |
|---|---|---|
| 早期独立 10 记录集合，P2 | **15.1 mm** | 早期记录 |
| 当前 18 矩阵，P2 三次 | **0.11 mm** | `s4_joint18` |

两者**分开标注**，不能混写。文档专门写了这句：

> 当前 18 矩阵 P2 三次运行的 spread 是 0.11 mm；早期独立 10 记录集合中 P2 曾出现 15.1 mm；两者在文档和 dashboard 中分开标注，不能混写。

**为什么差这么多？** 18 矩阵是同一 release、同一源码快照、连续跑的三次；早期集合跨了不同修订。所以这两个数的语义完全不同——一个是"同配置重复性"，一个是"跨版本稳定性"。

### 1.6 失败被分类保留，不是被删掉

| 失败 | 分类 | 处理 |
|---|---|---|
| S1/F1/P4 | 反馈停滞 + MAS 清理失败 + 关停原生崩溃 | 保留原始记录；根因未证实，**不归为**"动力学不可行" |
| 强流 U10/U15/U20 | `python_gate_refusal`（Python 证据不通过） | `real_started=false`，**不启动**真实试验 |
| 早期 S4 full gate | 门禁拒绝 | `formal_trials_started=false` |
| 相机 MP4 黑帧 | EGL 无法创建 dri2 screen | **不作为**视频证据，改用轨迹查看器 |

**"不启动"也是一种证据**。强流三项是"Python 先失败 → 门禁拒绝 → 真实后端根本没启动"，这比"启动了但失败"更有信息量：它说明门禁在工作。

### 1.7 不能声称的清单（原文摘录）

```
45 joint       ≠ 18 真实矩阵
5 条真实 pilot  ≠ 18 真实矩阵
18 Python      ≠ joint measured-current
F0/F1          ≠ measured-current
```

### 1.8 测试数量也不能跨快照比较

仓库里出现过这些数字：`622`（v0.5.1 验收）、`751`（Phase B 候选）、`847`（TerminalApproach）、`1187`（link_v6 回归）、`1229`（S4 规划）、`1256`（2026-11-20 全量）。

**它们不是"测试越来越多"的单调曲线**，而是不同快照、不同选择（`-k`、`--skip`）、不同环境下的计数。文档里对这一点也有说明（如"旧测试数量仅能归属旧报告"）。

论文里写"1256 passed"时必须带日期与命令，否则读者无法判断它对应哪个版本。

## 2. 严谨版：学术总结

### 2.1 证据分层的形式化

设主张集合 `C = {c_1, …, c_n}`，证据集合 `E = {E_P, E_R, E_J}`（Python / 真实 / 联合）。定义**支撑关系**

```
support: E → 2^C
```

则有效性要求：对每条被声称的 `c_i`，存在 `E_k` 使 `c_i ∈ support(E_k)` 且 `E_k` 的内部一致性检查通过。

| 证据 | 支撑的主张 | 不支撑的主张 |
|---|---|---|
| `E_P` | 控制律可行性、几何可通行、自研 3-DOF 闭环 | 6-DOF 耦合、饱和、时延 |
| `E_R` | 传输正确性、分配正确性、状态回写、进程生命周期 | 统计鲁棒性、海试 |
| `E_J` | 多障碍 + 可重复性（仿真内） | 实测流鲁棒性（因 §2.4）、真实 18 矩阵 |

**这是一个偏序结构**，不是全序：`E_J` 不"强于" `E_R`（前者是 45 条仿真矩阵，后者含 54 条真实链路），二者支撑不同主张。

### 2.2 统计口径的形式定义

| 口径 | 定义 | 本项目取值 |
|---|---|---|
| 逐条通过率 | `#pass / #total` | 54/54（Python）、53/54（真实） |
| 组通过（N6） | 每组 `≥ 4/5` 且 P0 成功且无安全违规 | 九组全通过 |
| 重复性（R2） | 同组两次运行指标差 ≤ 阈值 | 九组通过 |
| 名义条目 | 排除 repeat 的矩阵条目 | 44/45 |

**注意 N6 与逐条通过不等价**：N6 允许每组失败 1 条。故"九组 N6 通过"**不能**推出"54/54"。这是文档反复强调的一点。

### 2.3 指标定义与量纲

```
t_arr   [s]    首次满足 ‖p − g‖ ≤ 0.25 ∧ ‖ν‖ ≤ 0.1 ∧ |q| ≤ 0.1 且保持 0.5 s 的时刻
c_min   [m]    min_k dist(segment_k, ∂O)
m_safe  [m]    c_min − 0.9
e_rms   [m]    sqrt( mean_k ‖p_k − r_k‖² )
e_max   [m]    max_k ‖p_k − r_k‖
θ_max   [°]    max_k |θ_k|
f_sat   [-]    #{k : α_k < 0.999} / N
```

**归因注意**：`e_rms` 依赖参考轨迹。S4 消融中每条路径**用自己的参考**算误差（文档明确"每种方案按自身实际输入的参考路径计算误差"），故不同方案的 `e_rms` 不可直接比较"跟踪能力"，只能比较"相对各自参考的贴合度"。

### 2.4 F2 的时效性缺陷（可验证）

设 `c(t) = c_lin(t)·g(t)`，`g(t) = ½(1 + u/√(u²+ε))`，`u = (t−105)/45`，`ε = 0.01`。

在任务窗口 `[0, 61]` 内：

```
max_{t∈[0,61]} |c(t)| = 3.54×10⁻⁴ m/s        （t = 61 s）
而 F1 常流 = 5.0×10⁻² m/s
比值 ≈ 0.7%
```

**推论**：`E_J` 中 F2 与 F0 的数值差异（净距 0.17 mm、RMS 0.03 mm）与该比值一致；故

```
claim "控制器在实测流下保持性能"  ∉ support(E_J)
```

该主张只能由 F1（常流）支撑，且 F1 的流是**定常**的，不能替代"时变流"主张。

**这是实验设计的效度问题（construct validity），不是实现错误。** 修正方式（未实施）：把 gate 中心前移到任务窗口内，或延长任务至 onset 之后。

### 2.5 重复性的度量与解释

设同一配置三次运行的终态位置 `p^(1), p^(2), p^(3)`，定义

```
spread = max_{i,j} ‖p^(i) − p^(j)‖_∞
```

| 集合 | spread | 解释 |
|---|---|---|
| 18 矩阵 P2 | 0.11 mm | 同 release、同快照、连续运行 → 确定性验证 |
| 早期 10 记录 P2 | 15.1 mm | 跨修订 → 版本间稳定性 |

**语义差异**：前者验证"确定性实现"（第 1 段 §2.3 的逐位确定性主张），后者反映"版本漂移"。两者不可互相替代。

### 2.6 失败分类学

| 类别 | 定义 | 本项目实例 |
|---|---|---|
| **执行失败** | 后端启动且运行，未达判据 | S1/F1/P4（反馈停滞） |
| **前置拒绝** | 前置证据不通过，后端未启动 | 强流 U10/U15/U20（`real_started=false`） |
| **门禁拒绝** | 放行条件不满足 | 早期 S4 full gate（`formal_trials_started=false`） |
| **工具失败** | 采集/渲染失败，不影响控制 | 相机 MP4 黑帧 |
| **未归因** | 失败已记录，根因未证实 | S1/F1/P4 的起始原因 |

**关键纪律**：`未归因 ≠ 不可行`。文档明确写"起始原因未证实，不归为已证明的动力学不可行"——这在学术上是必要的谨慎，因为把"未查明"写成"不可行"是一种隐性过度声称。

### 2.7 外部效度边界

| 维度 | 覆盖 | 未覆盖 |
|---|---|---|
| 场景 | S1/S3/S4，静态矩形障碍 | 动态障碍、三维地形、非矩形 |
| 水流 | 零流、定常流、6 样本时变流（窗口外） | 垂直剪切、湍流、空间变化 |
| 初始态 | P0–P4（位置/俯仰） | 大姿态偏差、初始速度 |
| 载具 | 合成 `uuv_twin_axial_v2` | 真实艇、参数辨识 |
| 环境 | 平坦海底、无波浪 | 海况、盐度、温度 |
| 硬件 | 无 | 实艇、HIL |

### 2.8 局限（按严重度排序）

1. **F2 构造效度缺陷**：实测流在任务窗口内几乎为零（§2.4），使"实测流"这一实验因子实际未生效。
2. **单场景单流**：S4 消融只有 1 场景 × 1 流 × 1 初始，不能外推。
3. **真实矩阵有未归因失败**：S1/F1/P4 的根因未确立，影响"零故障"主张。
4. **强流仅 Python 拒绝**：真实后端未启动，故"强流不可行"是 Python 结论，不是真实结论。
5. **无统计检验**：未做置信区间、未做显著性检验；重复次数（2–3 次）不足以支撑分布推断。
6. **测试计数不可跨快照比较**：`622/751/847/1187/1229/1256` 分属不同快照。
7. **无可移植发布包**：干净环境复现仍是未完成项（C6）。
8. **相机视频无效**：EGL 限制导致黑帧，视觉证据只有查看器与静帧。
